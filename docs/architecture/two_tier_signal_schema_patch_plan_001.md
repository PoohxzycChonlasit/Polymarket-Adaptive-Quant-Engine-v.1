# TWO_TIER_SIGNAL_SCHEMA_PATCH_PLAN_001

This patch plan defines a safe sequence of updates to implement the two-tier signal attribution schema. It separates the execution trigger classification from the technical indicator state, keeping core strategy, EV, risk, and execution logic untouched.

---

## 1. Current Misleading Attribution Problem

Currently, the trading engine's update cycle calculates a technical indicator `SignalResult` (which defaults to `NO_SIGNAL` with reason `no_strategy_met_threshold` when indicators are quiet), and then independently estimates model EV. If EV is positive, a trade is opened. 

When logging the trade, the engine sets `signal_name` and `signal_reason` in the trade log to match the quiet technical indicators (`NO_SIGNAL`). This obscures the fact that the trade was actually generated by the model/EV engine, presenting incorrect statistics in performance reports.

---

## 2. Proposed Field Ownership

We will introduce a clear separation of fields:

* **Primary Execution Signal** (Why the trade was executed):
  * `signal_name`: Holds the execution category (e.g. `PROBABILITY_EV_EDGE` or strategy name if strategy triggers it).
  * `signal_reason`: Holds the execution reason (e.g. `yes_ev_above_threshold`, `no_ev_above_threshold`).
* **Strategy Telemetry Signal** (The state of the technical indicators):
  * `strategy_signal_name`: The raw rule-based strategy evaluated (`reversion`, `sniper`, `trend`, or `NO_SIGNAL`).
  * `strategy_signal_reason`: The raw reason returned by the technical strategy.

---

## 3. Propagation Map

Below is the flow of the two-tier fields from their creation point to the final analytical database:

```
[SignalResult]
  │ (strategy_signal_name, strategy_signal_reason)
  ▼
[Trader Update Loop] 
  │ Computes model EV. If approved:
  │   - Sets signal_name = "PROBABILITY_EV_EDGE"
  │   - Sets signal_reason = "[yes|no]_ev_above_threshold"
  ▼
[quant_detail Payload] (Compiles all 4 fields)
  ▼
[utils/quant_event_logger.py] (Validates and writes JSONL payload)
  ▼
[trade_journal/trade_open & trade_close] (Persisted JSONL lines on disk)
  ▼
[tools/edge_inventory_report.py] (Parses logs, groups, and exports metrics)
```

---

## 4. Edge Inventory Report Impact

* **Grouping**: The report will group closed trades by the primary `signal_name` (`PROBABILITY_EV_EDGE`) and sub-group by `signal_reason` (`yes_ev_above_threshold`).
* **Attributes**: The summary metrics tables will show performance breakdown under the correct execution signal name.
* **Telemetry**: Displays `strategy_signal_name` and `strategy_signal_reason` in the trade details table, giving researchers insight into what the technical indicators were doing when the model entered.

---

## 5. Legacy Handling

To prevent historical logs from breaking the reports or being classified as "unattributed legacy trades":
* In [tools/edge_inventory_report.py](file:///c:/quant/Polymarket-Adaptive-Quant-Engine-v.1/tools/edge_inventory_report.py), we will add a normalization step during loading.
* If a loaded event's `entry_attribution` does not contain `strategy_signal_name` or `strategy_signal_reason`, the parser will automatically backfill them:
  ```python
  if "strategy_signal_name" not in attribution:
      attribution["strategy_signal_name"] = attribution.get("signal_name", "NO_SIGNAL")
  if "strategy_signal_reason" not in attribution:
      attribution["strategy_signal_reason"] = attribution.get("signal_reason", "no_strategy_met_threshold")
  ```
This ensures 100% backward-compatibility and zero data-loss for old runs.

---

## 6. Patch Sequence

To prevent runtime or compiler errors, the patches must be implemented in order:

### Phase 1: Hardening the Reporting Tool
* Update `tools/edge_inventory_report.py` to declare `strategy_signal_name` and `strategy_signal_reason` as optional/valid attribution fields.
* Add the fallback/normalization logic in the row loaders.

### Phase 2: Updating the Event Logger Schema
* Update `utils/quant_event_logger.py` to permit `strategy_signal_name` and `strategy_signal_reason` in decision and execution payloads.

### Phase 3: Updating the Trader Metadata Compile
* Update [polymarket/trader.py](file:///c:/quant/Polymarket-Adaptive-Quant-Engine-v.1/polymarket/trader.py#L9113) inside the `clob_detail` dict compile to map:
  ```python
  is_model_trade = model_side in ("YES", "NO") and ev_result and ev_result.approved
  clob_detail = {
      ...
      "signal_name": "PROBABILITY_EV_EDGE" if is_model_trade else signal.signal_name,
      "signal_reason": f"{model_side.lower()}_ev_above_threshold" if is_model_trade else signal.signal_reason,
      "strategy_signal_name": signal.signal_name,
      "strategy_signal_reason": signal.signal_reason,
  }
  ```
